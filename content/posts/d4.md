# What Is MFA? Authentication Factors, Methods and Recovery

MFA stands for multifactor authentication. It requires more than one distinct authentication factor to sign in. Those factors concern something you know, have, or are. A password and a code from an authenticator can provide different factors. Two passwords do not.

The method matters because different forms of MFA resist different threats. A code can add protection while remaining vulnerable to phishing. Some cryptographic methods bind authentication to the legitimate service instead.

For businesses, enabling a setting is only one part of implementation. Teams also need enrollment, enforcement, recovery, and a process for suspicious sign-ins.

## What Counts as an Authentication Factor?

An authentication factor provides evidence that the person signing in controls an account's authenticator. The familiar categories are knowledge, possession, and inherence. MFA combines distinct factors rather than simply adding another screen. One authenticator can also incorporate more than one factor.

The [NIST digital identity guidelines](https://pages.nist.gov/800-63-4/sp800-63b.html) distinguish authenticator types and their security properties. They also explain requirements for different authentication assurance levels.

The three factor categories work as follows:

| Factor | Plain meaning | Example |
|---|---|---|
| Knowledge | Something you know | A password or authenticator activation PIN |
| Possession | Something you have | Control of a registered cryptographic key or OTP authenticator |
| Inherence | Something you are | A biometric comparison, such as a fingerprint |

Two knowledge checks remain the same factor category. Asking for a password and another memorized secret does not create multifactor authentication.

A biometric comparison also needs context. Under NIST's guidelines, a biometric characteristic alone does not qualify as an authenticator.

For example, a fingerprint can activate a cryptographic authenticator on a device. The device provides possession, while the biometric comparison provides another factor.

The number of visible prompts does not tell you how many factors the system verifies. Review the authentication method and configuration.

## How Does MFA Work During Sign-In?

MFA verifies different evidence before granting access. In a password-and-code flow, the user supplies a password and a registered authenticator's output. Other methods use a cryptographic key with local user verification. The exact sequence depends on the service and selected authentication method.

A basic password-and-authenticator flow usually follows this pattern:

1. The user opens the legitimate application or sign-in page.
2. The service checks the supplied password.
3. The service requests evidence from a registered authenticator.
4. The user completes that request through the expected method.
5. The service evaluates the authentication and applicable access policy.

Do not interpret this sequence as a universal interface. A passkey-based flow can look different and need no account password.

Authentication also differs from authorization. Successful sign-in does not determine which records someone should access.

An employee may authenticate correctly while retaining permissions they no longer need. [Identity management across role changes](/cybersecurity/okta-identity-security/) addresses that separate operating problem.

## Which MFA Methods Resist Phishing?

Phishing-resistant authentication prevents a fake service from obtaining usable authentication evidence through ordinary credential phishing. Manually entered codes do not provide that property. Cryptographic methods can bind authentication to the intended service. The protocol and configuration determine the protection, not the product's marketing label.

NIST explains how [phishing-resistant authentication protects sign-in secrets](https://www.nist.gov/blogs/cybersecurity-insights/phishing-resistance-protecting-keys-your-kingdom). It removes reliance on users noticing every convincing imitation sign-in page.

Compare common approaches carefully:

| Method | Practical distinction | Phishing resistance |
|---|---|---|
| Password plus SMS code | Uses a code delivered through the phone network | Not phishing-resistant |
| Password plus authenticator-generated code | Uses a code generated by an enrolled authenticator | Not phishing-resistant |
| Password plus simple push approval | Asks the user to approve a sign-in request | Not phishing-resistant |
| Password plus number-matching push | Requires matching information from the sign-in flow | Does not establish phishing resistance |
| FIDO/WebAuthn passkey with user verification | Uses service-bound cryptography and local verification | Supports phishing-resistant MFA |

The table compares methods, not specific products or every available configuration. A hardware device can support several protocols with different properties.

### Why One-Time Codes Can Still Be Phished

A one-time code limits reuse, but a recipient can still disclose it to an impostor. An attacker may relay a valid code during the sign-in attempt.

Never give authentication codes to someone who contacts you unexpectedly. A request framed as technical support does not change that rule.

SMS also depends on the phone-number delivery channel. That introduces risks distinct from authenticator-generated codes.

Do not disable existing MFA while planning stronger authentication. Improve the method through a controlled transition that preserves account access.

### What Makes Passkeys Different

Passkeys use public-key cryptography rather than a shared password for the sign-in exchange. The authentication process binds the credential to the relevant service.

When the method requires a PIN or biometric verification, it can provide multiple factors. Not every passkey configuration automatically satisfies every assurance requirement.

A security-key touch alone can demonstrate user presence without proving an additional factor. Administrators must check whether the chosen flow requires user verification.

Passkeys can be device-bound or syncable. Those arrangements create different management and recovery considerations, especially for privileged accounts.

## Is Number Matching the Same as Phishing-Resistant MFA?

No, number matching and phishing resistance describe different protections. Number matching improves on a simple approval prompt by requiring information from the sign-in attempt. It does not provide the same service binding as phishing-resistant cryptographic authentication. Treat it as a specific improvement, not an equivalent label.

CISA recommends [stronger MFA methods for business accounts](https://www.cisa.gov/audiences/small-and-medium-businesses/secure-your-business/require-multifactor-authentication). Its guidance describes number matching as an interim step toward phishing-resistant authentication.

Employees should still reject unexpected prompts. Repeated requests do not become legitimate because they interrupt work.

If someone claims that approving a prompt will fix a problem, verify that claim independently. Do not use contact information supplied with the suspicious request.

## What Is the Difference Between Enrollment and Enforcement?

Enrollment connects an authenticator to an account. Enforcement determines when the service requires the authentication method. An enrolled user may still encounter access routes that do not require it. Check actual sign-in policy and behavior rather than relying only on registration counts.

For each important application, record these details:

- Which employees and administrators have registered an approved method.
- Which access routes require that method.
- Which users or applications have exceptions.
- Which fallback methods remain available.
- Who owns each exception and its review date.

Test the routes employees use, including supported mobile and remote-access flows. Review older access methods that may behave differently.

A dashboard saying that users have registered MFA does not demonstrate complete coverage. Inspect successful sign-ins and the policies that governed them.

This distinction complements cloud access and misconfiguration analysis. A control's availability does not prove that the organization applies it consistently.

## How Should Account Recovery Work?

Recovery restores access when an employee loses an authenticator or cannot complete the normal process. That makes recovery part of the security design. Define who can authorize changes and what evidence they require. Avoid improvised exceptions that bypass the protection of ordinary sign-in.

An organization should decide these issues before rollout:

- How employees register an approved backup method.
- How they report a lost device or security key.
- How support verifies a request to replace an authenticator.
- How administrators invalidate a lost or compromised method.
- How the organization records and reviews recovery actions.

Do not ask employees to share their authentication secrets with support staff. Support procedures should verify the request through approved processes.

Recovery codes, where offered, need secure storage. They can provide access and should not circulate through ordinary workplace chat.

Test recovery with the support team before enforcing a new method broadly. Include employees who cannot use a personal phone or need accessibility accommodations.

For privileged accounts, document emergency-access arrangements separately. Such access needs appropriate protection, monitoring, and periodic review.

## Does Single Sign-On Replace MFA?

Single sign-on and MFA address different parts of access. SSO lets users access connected applications through a central sign-in arrangement. MFA strengthens the authentication event. A business can combine them, but centralizing sign-in does not automatically enforce strong authentication everywhere.

Check each application's relationship with the identity provider. Confirm how it handles authentication requirements, sessions, and alternative sign-in routes.

Also check what happens after an employee leaves. Removing central access may not address every separate account or existing session automatically.

Name the owner of each application's access policy. The identity team and application administrator should agree on their responsibilities.

## What Should a Business Test Before Rollout?

A useful pilot tests ordinary sign-in alongside failure and recovery scenarios. Choose representative employees, devices, and applications. Record results rather than assuming success from enrollment alone. Resolve operational barriers before expanding the policy to the wider organization.

Use a practical test list:

1. Register the approved method through the legitimate enrollment process.
2. Sign in through each supported device and application route.
3. Confirm that the intended policy requires the approved method.
4. Reject an unexpected prompt and follow the reporting process.
5. Recover access through the approved backup procedure.
6. Remove a lost authenticator and confirm the change.
7. Review the event records with the responsible administrator.

Do not conduct an unannounced production lockout as a test. Coordinate the pilot and ensure support can handle problems.

Start prioritization with privileged access and sensitive business functions. Then document the plan for remaining users and applications.

Avoid measuring success only through the number of registered devices. Coverage, exceptions, recovery quality, and sign-in behavior all need review.

## What Should Employees Do with Unexpected MFA Prompts?

Reject unexpected prompts and report them through a trusted support channel. Do not approve repeated requests to make them stop. Describe when the prompts appeared and whether you interacted with them. If you approved one accidentally, tell the response team promptly.

An unexpected prompt does not by itself prove every detail of an attack. Administrators need to inspect account activity and relevant logs.

If you also received a suspicious email, report both events together. The [phishing email response steps](/cybersecurity/phishing-email-examples/) list the details to include, and the sequence can help investigators establish what happened.

MFA does not eliminate every risk after authentication. Compromised endpoints, stolen sessions, and excessive permissions require their own controls and response procedures. For the wider threat picture, see the [cybersecurity statistics](/cybersecurity/cybersecurity-statistics/) overview.

## Frequently Asked Questions


### Is Two-Factor Authentication the Same as MFA?

Two-factor authentication uses exactly two distinct factors. It is a form of multifactor authentication.

### Does a Password Plus a Security Question Count as MFA?

No, both usually rely on something you know. Adding another knowledge check does not add a distinct factor category.

### Can One Device Provide Multiple Factors?

Yes, a cryptographic authenticator can require a PIN or biometric to activate it. The configuration must verify the distinct factors.

### Does MFA Prevent Every Account Compromise?

No, protection depends on the method, configuration, recovery process, and surrounding controls. Phishing-resistant MFA addresses important sign-in threats without eliminating every account or device risk.

Inventory your critical accounts and their actual authentication methods. Confirm enforcement, document exceptions, and test recovery before expanding the rollout. Strong authentication works best when employees and administrators can operate it consistently.
